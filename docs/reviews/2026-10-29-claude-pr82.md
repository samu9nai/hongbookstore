| 항목 | 판정 | 근거 수준과 위치 |
|---|---|---|
| 1. 구해요 도메인의 신원 출처 | 동의 | **실행 확인·소스 확인.** `domain/wanted/controller/WantedController.java:42,45,51,55,63,66`과 `domain/comment/controller/WantedCommentController.java:33,37,45,50,58,62`가 `@AuthenticationPrincipal LoginUserDTO`의 `id()`만 쓴다. `/api/wanted`를 매핑하는 컨트롤러는 이 둘뿐이다. 백엔드 `src/main` 전체에서 `X-User-Id`·`X-USER-ID`·`X-USER-NICKNAME`을 찾으면 `config/SecurityConfig.java:149`의 CORS 주석 한 줄만 남는다. `getHeader(`·`@RequestHeader`는 `auth/jwt/JwtTokenProvider.java:115`, `auth/controller/AuthController.java:23`, `domain/mypage/controller/MyPageController.java:109`에 있고 모두 `Authorization` 토큰을 읽는다. 사용자 ID를 헤더로 읽는 곳은 없다. 다른 도메인의 경로·바디 사용자 ID(SEC-01, SEC-04)는 이 PR의 범위가 아니다 |
| 2. `loginUser`가 null일 가능성 | 동의 | **실행 확인·소스 확인.** `config/SecurityConfig.java:109-110`은 `POST`·`DELETE /api/wanted/**`에 `STUDENT`·`ADMIN`을 요구하고, `PUT`은 `:117`의 `anyRequest().authenticated()`로 떨어진다. 인증 객체를 만드는 곳은 `auth/jwt/JwtAuthFilter.java:57-63`뿐이고 주체는 항상 `LoginUserDTO`다. 세션은 STATELESS(`SecurityConfig.java:54-55`)라 OAuth2 주체가 이 경로에 남지 않는다. 임시 테스트로 토큰 없이 `PUT`·`POST`·`DELETE /api/wanted`와 댓글 `POST`를 보내 모두 302(로그인 페이지)를 확인했다. NPE·500은 나지 않는다. API가 401 대신 302를 주는 것은 기준 커밋부터의 동작이다 |
| 3. 댓글 `nickname`에 DB `username` 저장 | 부분 동의 | **소스 확인.** 응답 누출은 없다. `nickname`을 읽는 곳은 `domain/comment/dto/WantedCommentDto.java:37`뿐이고, 이 DTO를 내보내는 세 경로가 모두 `nickname(null)`로 덮는다(`domain/comment/service/WantedCommentService.java:76,142,195`). `WantedComment`를 쓰는 코드는 `domain/comment` 밖에 없다. 다만 저장값이 실제로 바뀐다. 기준 커밋에서 JWT 주체는 `getNickname`·`getName`·`getUsername` 호출이 모두 실패해 `"익명"`이 됐고(`96ceff7` `WantedCommentService.java:256-261`), 그 뒤 `X-USER-NICKNAME` 분기(`:272-276`)는 닉네임이 비어 있을 때만 실행되므로 도달하지 않았다. 따라서 이전 저장값은 항상 `"익명"`이었다. PR 본문의 "이전에는 헤더 값이나 `익명`이었다"는 부정확하다. 이 PR부터 익명 게시판 댓글 테이블에 실제 닉네임이 쌓이고, `User.updateProfile`(`domain/user/domain/User.java:49`)로 닉네임을 바꾸면 저장값이 낡는다. 원래 코드의 의도(실닉 저장 후 숨김)와는 맞으므로 결함으로 보지 않고, 리뷰가 필요한 결정으로 남긴다 |

PR 본문의 재현 주장과 같다. 리뷰 HEAD에서는 6개 모두 통과한다. `ModerationService` 목은 소유자 검사를 가리지 않는다. `domain/wanted/service/WantedService.java:109-110`의 소유자 검사가 `:113-118`의 유해 표현 검사보다 먼저다. **공백:** 답글 작성 `POST /{wantedId}/comments/{parentId}/replies`(`WantedCommentController.java:42-52`)는 같은 취약점이 있던 경로인데 테스트가 없다. 임시 테스트로 남의 토큰과 `X-USER-ID`·`X-USER-NICKNAME` 헤더를 보내 201, 저장된 `userId`가 토큰 주인, `nickname`이 토큰 주인의 `username`임을 확인했다. 동작은 맞으므로 회귀 방지용 테스트 추가를 권한다 |
| 5. 프론트 헤더 제거 | 동의 | **실행 확인·소스 확인.** 지운 변수(`uidRaw`·`uid`, `WantedDetail`의 `userId`)는 다른 곳에서 쓰지 않는다. `pnpm type-check`, `pnpm format:check`, 바꾼 3개 파일의 `oxlint --type-aware --max-warnings=0`이 통과했다. 참고: `frontend/src/features/wanted/WantedWrite.tsx:828`의 `ensureUserId()`(`:89-123`)는 이제 로그인 여부 판정에만 쓰인다. 원래 목적이던 헤더 값이 없어졌는데, `localStorage`에 `userId`가 없고 토큰 페이로드에서도 못 찾으면 `window.prompt`로 "테스트용 userId"를 묻는 경로가 남아 있다. 고아 변수는 아니므로 이 PR의 결함으로 세지 않고 후속 정리를 제안한다 |
| 6. 문서 갱신 | 동의, 사소한 지적 3건 | **소스 확인.** `docs/backlog.md:143`의 SEC-02 완료 요약과 `:117`의 BE-03 갱신, `AGENTS.md:44`의 테스트 수 13개는 실행 결과와 맞는다. 사소한 지적: ① `AGENTS.md:42`의 열 제목은 여전히 "현재 기준선 (2026-10-22)"인데 백엔드 행만 10-29 기준으로 바뀌었다 ② `docs/backlog.md:23`의 "다음 작업 순서"가 아직 SEC-02를 할 일로 적는다 ③ 완료 표에서 SEC-02(`:143`)가 SEC-16 뒤에 있어 ID 순서가 어긋난다 |

## 실행하지 않은 검증과 이유

- 브라우저에서 구해요 글 작성·수정·삭제와 댓글 작성·삭제를 직접 해 보지 않았다. 로컬 MySQL·Redis와 OAuth 로그인 환경이 없다.
- `pnpm build`, `pnpm test:unit`, `pnpm test:e2e`, 전체 `pnpm lint`는 다시 실행하지 않았다. 프론트 변경은 헤더 3곳 삭제뿐이라 타입·서식·린트로 충분하다고 판단했고, 원격 CI가 이 검사들을 통과했다.
- MySQL에서 `WantedComment.nickname` 컬럼 길이와 `username`(25자)의 호환성을 실제 DB로 확인하지 않았다. 엔티티의 `@Column(name = "nickname")`은 길이를 지정하지 않아 기본 255자이므로 문제가 없다고 추론했다(위험 추론).
- 운영 DB에 이미 저장된 댓글의 `nickname` 값 분포는 확인하지 않았다. 소스상 `"익명"`이었을 것으로 추론했다.
