## 수정 요청

### R1. [P3] Location의 끝부분 대신 해석한 목적지를 비교한다

- 판정: **반박** — 절대·상대 URI 허용이 아니라 현재 `endsWith("/login")`의 검증 범위에 대한 판정이다.
- 근거 수준: **실행 확인**(matcher 반례), **소스 확인**(테스트·보안 설정), **위험 추론**(향후 잘못된 목적지를 놓칠 가능성).
- 위치: `backend/src/test/java/com/hongik/books/ApiContractTest.java:111-117` (`d668e0f`, head에도 동일).

현재 테스트는 `302`와 Location의 suffix만 검사한다. 저장소 캐시의 Hamcrest 3.0으로 matcher를 직접 실행했을 때 다음 여섯 값이 모두 통과했다.

| Location | 현재 matcher | 요청 origin을 기준으로 해석한 목적지가 정확히 `/login`인가 |
|---|---|---|
| `/login` | 통과 | 예 |
| `http://localhost/login` | 통과 | 예 |
| `/other/login` | 통과 | 아니요 |
| `https://example.invalid/login` | 통과 | 아니요 |
| `//example.invalid/login` | 통과 | 아니요 |
| `http://localhost?next=/login` | 통과 | 아니요 |

따라서 경로뿐 아니라 origin·query가 바뀌어도 테스트가 성공할 수 있다. 이 결과는 실제 서버가 위 주소로 리다이렉트한다는 뜻이 아니다. **테스트가 잘못된 목적지를 거르지 못한다는 사실만 재현했다.**

**요청:** Location을 요청 URI에 대해 `URI.resolve`한 뒤 예상 URI 전체와 비교하거나, 이 MockMvc 요청에서 허용하는 `/login`과 `http://localhost/login`만 정확히 허용한다. `URI.getPath()`만 검사하면 다른 origin은 계속 허용하므로 목적지 전체를 비교한다. `302` 단언은 유지한다. BE-05로 기록했다.

**테스트의 범위에는 부분 동의한다. “프론트 응답 계약 전체가 보존됐다”는 해석에는 동의하지 않는다.** PR 본문의 보장 범위도 “여섯 시나리오에서 단언한 응답 항목”으로 한정하는 것이 정확하다.

보완 우선순위는 다음과 같다. 아래는 아직 관찰하지 못한 제품 장애를 새 결함으로 단정하는 항목이 아니라 BE-03의 테스트 범위 제안이다.

1. 목록·상세·오류·프로필의 `Content-Type`을 검사한다. 특히 구해요 화면은 `application/json`이 아니면 JSON 본문이 있어도 데이터로 읽지 않는다(`Wanted.tsx:225-237`, `WantedDetail.tsx:546-553`). SSE도 `text/event-stream`을 확인한다.
2. SSE 구독 뒤 `NotificationService.sendToUser`로 값이 채워진 `CHAT` 또는 `WANTED_COMMENT` 알림을 보내고, `data:`를 JSON으로 파싱해 헤더가 읽는 필드를 비교한다. 현재 `data:{"id":` 단언은 프론트가 요구하지 않는 JSON 필드 순서까지 고정한다. `sendInternal`의 Jackson 3 전환을 검증하려면 실제 소비 필드가 더 유용하다(`backend/src/main/java/com/hongik/books/domain/notification/service/NotificationService.java:160-178`).
3. 기존 fixture에 이미 있는 목록의 저자·가격·분류·학과와 값이 있는 `profileImageUrl`을 검사한다. `condition="상"`은 화면이 지원하는 과거 데이터라 틀린 fixture는 아니지만 현재 값인 `HIGH`도 대표 사례로 유용하다(`Wanted.tsx:28,457-470`).

`PageImpl` 경고를 없애려고 이 PR에서 응답을 DTO로 재설계할 필요는 없다. 기존 응답 모양의 비교와 앞으로의 공개 계약 설계는 구분한다. 후자는 OPS-11에 이미 기록돼 있다. 작성자 이름·조회수가 없는 구해요 상세 문제(FE-23)도 이 PR의 신규 회귀로 계산하지 않았다.

## ② Location 단언을 완화한 근거

**절대·상대 URI 표기 차이를 허용하는 방향에는 동의한다. “프레임워크 업그레이드와 무관한 차이”라는 `d668e0f` 커밋 설명에는 반박한다.**

[Spring Security 7 마이그레이션 문서](https://docs.spring.io/spring-security/reference/6.5/migration-7/web.html)는 로그인 리다이렉트가 상대 URI를 선호하도록 바뀌었다고 명시한다. 로컬 캐시의 Security 6.5.7 소스에서도 `LoginUrlAuthenticationEntryPoint.favorRelativeUris=false`를 확인했다. Security 7.1.1 JAR을 `javap`으로 읽으면 생성자가 이 필드를 true로 설정한다. head의 Boot BOM은 Security 7.1.1을 지정한다. 이는 **소스·바이트코드 확인**이며 서버 HTTP 재현과는 다르다.

한편 Boot 4.1.1의 `spring-boot-tomcat` 설정 메타데이터는 `server.tomcat.use-relative-redirects`의 기본값을 false로 명시한다. [Boot 설정 문서](https://docs.spring.io/spring-boot/appendix/application-properties/index.html#application-properties.server.server.tomcat.use-relative-redirects)도 이 속성이 `sendRedirect`의 Location 표기를 결정한다고 설명한다. 저장소는 이 값을 덮어쓰지 않는다. 따라서 Security가 상대 URI를 넘겨도 실제 Tomcat이 절대 URI로 반환했다는 작성자의 관찰은 설정과 일치한다.

작성자는 PR 본문에 두 버전의 `RANDOM_PORT` 서버를 리다이렉트를 따르지 않는 HttpClient로 호출해 모두 `302`, `http://localhost:<port>/login`을 확인했다고 적었다. 이 보고와 공식 변경 설명은 표기 차이의 근거로 충분하다. 다만 임시 테스트가 PR에 없고 리뷰어의 재실행도 차단됐으므로, 이 리뷰는 해당 결과를 **작성자 보고**로만 인용한다.

다음 세 가지를 구분해서 기록하는 것이 정확하다.

- Security 7이 상대 URI를 선호하도록 바꿨다.
- MockMvc에는 실제 Tomcat의 리다이렉트 변환이 없어서 그 차이가 보인다.
- 작성자는 기본 Tomcat 설정의 직접 HTTP 요청에서 최종 Location이 같았다고 보고했다. 프록시·다른 origin·context path까지 같다는 보장은 아니다.

현재 `application.yml:134-137`은 `forward-headers-strategy: framework`를 쓴다. 프록시 헤더가 있는 요청이나 브라우저의 최종 화면 이동은 이번 검증 범위 밖이다. 이를 확인하지 않고 운영 경로 전체에서 차이가 없다고 확장하지 않는다. 테스트만 통과시키려고 Security 설정을 과거 기본값으로 되돌릴 필요도 없다.

## ③ Tomcat·Jackson 덮어쓰기의 PR 포함 여부

**`01cd62b`를 이 PR에 유지하는 데 동의한다.** `docs/decisions.md:37`의 D-U는 Boot 관리 버전에 공개 취약점이 남으면 같은 minor의 패치로 덮어쓰도록 정했다. `backend/build.gradle.kts:22-26`은 그 범위 안에 있다. 보안 결함을 해결하려고 Boot를 올리는 PR에서 관리 BOM의 오래된 패치를 그대로 남기는 것보다 변경 목적에 맞는다.

| 계열 | Boot 4.1.1 BOM의 기본값 | 이 PR의 지정값 | 판단 |
|---|---|---|---|
| Tomcat | 11.0.24 | 11.0.27 | 같은 11.0 계열의 보안 패치 |
| Jackson 3 BOM | 3.1.5 | 3.1.8 | MVC와 변경된 SSE 직렬화에 관련된 같은 3.1 계열 패치 |
| Jackson 2 BOM | 2.21.5 | 2.21.8 | 잔존 Jackson 2 사용처를 위한 같은 2.21 계열 패치 |

기본값은 로컬 Gradle 캐시의 `spring-boot-dependencies-4.1.1.pom`을 XML로 읽어 확인했다. 지정값은 head의 빌드 파일에서 확인했다. 이 표는 **BOM·빌드 소스 확인**이다. 이번 리뷰에서 전체 해석 결과를 출력하지 못했으므로 모든 런타임 아티팩트의 선택 버전을 재검증했다는 뜻은 아니다.

공식 자료에서도 패치를 유지할 근거를 확인했다.

- [Apache Tomcat 보안 공지](https://tomcat.apache.org/security-11.html#Fixed_in_Apache_Tomcat_11.0.27)는 11.0.24 이후의 수정 사항을 명시한다. 예를 들어 11.0.27은 비동기 HTTP/2 처리 중 요청·응답이 섞이는 CVE-2026-101356을 수정한다. 이 애플리케이션에서 해당 취약점을 악용할 수 있는지는 검증하지 않았다.
- [Jackson 3.1.8](https://github.com/FasterXML/jackson/wiki/Jackson-Release-3.1.8)과 [Jackson 2.21.8](https://github.com/FasterXML/jackson/wiki/Jackson-Release-2.21.8)의 공식 릴리스 기록은 databind의 CVE-2026-110879 수정을 포함한다. Avro·CBOR 등 사용 여부가 확인되지 않은 모듈의 CVE를 애플리케이션 위험 건수에 더하지 않았다.
- Jackson 2는 아직 필요하다. `build.gradle.kts:63-66,74-75,86`에 JJWT Jackson 어댑터와 Jackson 2 모듈이 남는다. `WantedCommentService.java:46,359`, `KmaClient.java:21,51`, `PlaceService.java:47,131`도 Jackson 2 파서를 직접 쓴다. 이 Java 파일들의 루트는 `backend/src/main/java/com/hongik/books/domain`이며 각각 `comment/service`, `weather/kma`, `place/service` 아래에 있다.

[Boot의 Gradle 의존성 관리 문서](https://docs.spring.io/spring-boot/gradle-plugin/managing-dependencies.html#managing-dependencies.dependency-management-plugin.customizing-managed-versions)는 현재 사용하는 dependency-management 플러그인에서 `extra[...]`로 BOM 속성을 덮어쓰는 방식을 지원한다. 다만 Boot가 검증한 조합을 벗어나므로 패치 버전이라는 이유만으로 모든 호환성을 보장할 수는 없다.

후속 기준은 다음처럼 적용하는 것이 좋다.

- OPS-11(`docs/backlog.md:121`)에서 각 덮어쓰기를 추적한다. 다음 Boot 패치가 해당 보안 수정 이상을 관리하는지 확인한 뒤 **해당 줄별로** 제거한다. 단순히 Boot 버전이 올라갔다고 세 줄을 일괄 삭제하지 않는다.
- 제거할 때 해석된 `runtimeClasspath` 좌표와 테스트 결과를 확인한다. 패치가 실제로 낮아지지 않는지 확인한다.
- `renovate.json`에는 이 세 `extra[...]`에 대한 별도 매핑이 없다. Renovate가 자동으로 추적한다고 가정하지 않는다. 이번 리뷰에서는 Renovate 추출기를 실행하지 않았으므로 추적 불가능하다고 단정하지도 않는다.

SEC-15와 PR 본문의 `167개 모듈`, `10건 → 0건`, 심각도별 집계는 작성자의 측정값이다. 이번 리뷰는 전체 좌표 추출과 OSV querybatch를 재실행하지 못했다. 공식 보안 수정의 존재는 확인했지만, 이 수치 전체를 독립 검증한 것으로 표시하지 않는다. OSV 0건도 알려진 패키지 권고의 조회 결과이며 애플리케이션의 기존 SEC 결함 해결을 뜻하지 않는다.

## 실행하지 못한 검증과 이유

1. **업그레이드 전후 테스트 재실행과 실제 Tomcat Location 비교:** `78d2fc2`, `d668e0f`, `a63fe1b`, `af85792`의 추적된 backend 파일만 임시 사본으로 추출했다. `.env`는 복사하지 않았다. `d668e0f`와 head에는 리다이렉트를 추종하지 않는 실제 HttpClient 검사 및 소비 필드·값이 있는 SSE 검사를 준비했지만 Gradle wrapper의 사용자 캐시 잠금 파일 접근이 거절돼 테스트가 시작되지 않았다. 권한 확장 재실행도 자동 승인 검토의 사용량 한도로 거절됐다. 안전하지 않다는 판정이 아니라 승인 검토 자체의 실패였다. 준비한 임시 검사는 통과 건수에 넣지 않았다.
2. **전체 런타임 모듈 추출과 OSV 재조회:** 임시 Gradle 태스크와 현재 작업 폴더의 읽기용 의존성 추출 모두 같은 캐시 권한 문제로 시작하지 못했다. 전체 선택 좌표를 확보하지 못해 OSV 집계도 재현하지 않았다. 캐시의 BOM 기본값 확인으로 범위를 한정했다.
3. **실제 MySQL·Redis·OAuth·외부 API·메일·STOMP:** 이 리뷰에서 해당 서비스와 인증 환경을 기동하지 않았다. H2와 Redis 목은 DB 방언·실제 블랙리스트·외부 통신의 대체 증거가 아니다.
4. **프록시·브라우저에서 최종 로그인 화면과 업무 알림 표시:** 실제 서버 비교를 실행하지 못했다. 브라우저에서 백엔드와 연결한 사용자 흐름도 실행하지 않았다.
5. **로컬 프론트 검사 전체 재실행:** 프론트 변경이 없어 소비 코드를 읽고 지정 head의 원격 CI를 확인했다.

## 리뷰어의 변경과 후속 작업

리뷰어는 이 문서를 추가하고 `docs/backlog.md`에 BE-05(Location 단언의 목적지 검증 누락)를 추가했다. 애플리케이션과 테스트 소스, 빌드 설정, 결정 기록은 수정하지 않았다. GitHub 댓글·리뷰 게시, 커밋·push·병합은 수행하지 않았다.

작성자는 R1의 목적지 단언을 보완하고, 리다이렉트 차이의 원인을 Security 7 기본값 변경과 Tomcat 변환으로 구분해 설명하는 것이 좋다. 소비 계약의 추가 검사는 BE-03, 덮어쓰기 제거와 Page 응답 설계는 OPS-11에서 추적한다. 권한 문제가 해소되면 업그레이드 전후 실제 서버 비교와 전체 런타임 좌표·OSV 조회를 다시 실행해야 한다.
