## R1 — [P2] auth에서 app의 i18n 초기화 모듈을 가져오지 않는다

- 판정: **부분 동의**. 기능 배치는 D-P와 맞지만 의존 방향은 일부 어긴다.
- 근거 수준: **소스 확인**. 앱 오류나 순환 import를 재현했다는 뜻은 아니다.
- 위치: `frontend/src/features/auth/Login.jsx:3`, `frontend/src/features/auth/Register.jsx:3`.
- 계약: `docs/decisions.md:32`의 `app → features → shared`.
- 백로그: FE-20.

두 파일은 `import '@/app/i18n.js'`로 상위 층을 직접 가져온다.
따라서 auth 컴포넌트를 독립적으로 가져와도 앱 전체 번역 리소스와 전역 i18n 초기화를 실행한다.
이번 PR이 약속한 기능별 의존 경계가 이 두 곳에서는 성립하지 않는다.
PR 본문의 의존 방향 검사도 `features → app`을 빠뜨려 이 위반을 잡지 못했다.

작성자는 두 side-effect import를 제거하고 앱에서 초기화를 맡기는 최소 수정을 검토하면 된다.
`frontend/src/app/App.jsx:10`은 이미 `./i18n.js`를 가져온다.
이는 새 구조를 제안하는 지적이 아니라 이번 PR에서 정한 D-P를 완성하기 위한 지적이다.
수정 후에는 두 경로가 사라졌는지 확인하고 로그인 화면의 번역 초기화를 검증해야 한다.

## 로컬 자동 검사

최종 주요 검사는 macOS, Node 24.21.0, pnpm 12.8.1에서 실행했다.
명령 앞에 `fnm exec --using 24.21.0`을 붙여 저장소 버전을 선택했다.
초기 기본 셸의 Node 26.11.0 결과와 구분한다.

| 검사 | 결과 |

첫 e2e는 샌드박스의 localhost listen EPERM으로 서버를 시작하지 못했다.
권한을 올린 재실행은 통과했다. 임시 소스 사본에서 pnpm이 의존성 설치를 시도하며
네트워크 대기 상태에 들어가 해당 실행을 중단하고, 설치된 Vite CLI를 Node로 직접 실행했다.
리뷰어가 저장소 루트에서 Vite를 직접 호출한 한 번의 시도는 index.html을 찾지 못했다.
최종 빌드 비교는 각 사본의 frontend 디렉터리에서 실행한 결과다.

## 실행하지 않은 검증과 남은 위험

- 실제 백엔드·MySQL·Redis를 기동해 로그인과 각 기능을 조작하지 않았다. 이번 검토는 소스 비교와 프론트 검사에 한정했다.
- 실제 네이버 지도 SDK와 길찾기를 실행하지 않았다. 비교 빌드에 자격 증명을 넣지 않아 일부 환경 변수 분기는 소스 diff로만 확인했다.
- 로컬 Gradle 테스트는 실행하지 않았다. 백엔드 변경이 없으며 원격 백엔드 CI 결과만 확인했다.
- 개발 서버 모드 e2e와 배포 환경은 별도로 실행하지 않았다. 로컬 브라우저 검증은 프로덕션 빌드의 preview 모드다.
- R1 수정 후의 번역 표시 검증은 실행하지 않았다. 리뷰 대상 앱 코드를 수정하지 않았다.
- 큰 청크와 stompjs의 net 외부화 경고는 남아 있다. 기존 FE-02·FE-05·FE-06 및 보안 백로그를 이번 PR이 해결한 것으로 해석하지 않는다.
