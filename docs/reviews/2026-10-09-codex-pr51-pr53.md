## 지적 사항

### R1 — [P3] MapPlace에 서버가 허용하는 null을 반영한다

- 판정: **부분 동의**. DTO의 필드와 기본 타입은 맞지만 nullable 계약은 일치하지 않는다.
- 위치: `frontend/src/components/NaverMap/Navermap.tsx:23-24` (`67ee7de`).
- 근거 수준: **소스 확인**, **실행 확인**(TypeScript 반례). 실제 API·DB 응답은 실행하지 않았다.
- 백로그: FE-18.

`MapPlace`는 `category?: string`, `description?: string`으로 두 필드의 생략만 허용한다.
백엔드 `Place.java:32-35`는 두 필드에 NOT NULL 제약을 두지 않는다.
`PlaceService.java:153-158`은 요청 값을 그대로 저장하고,
`PlaceDto.java:49-50`은 엔티티 값을 응답에 그대로 넣는다.
이 근거 위치는 모두 `67ee7de` 기준이며 이번 PR에서 바뀌지 않은 백엔드 코드다.

따라서 두 값이 null인 저장 장소를 현재 인터페이스로 표현할 수 없다.
임시 checkout에서 아래 값에 프로젝트 타입 검사를 적용하면 두 필드 각각 TS2322가 발생한다.

```ts
const nullablePlace: MapPlace = {
  id: 1,
  name: '장소',
  address: '주소',
  lat: 37.55,
  lng: 126.92,
  category: null,
  description: null
}
```

작성자는 두 필드를 `string | null`도 허용하도록 고치고, 해당 필드를 받는 헬퍼 인자도 맞추는 것이 좋다.
이는 실행 동작을 바꾸지 않는 수정이다. 현재 코드의 fallback 때문에 즉시 화면이 깨진다는 지적은 아니다.
다음 단계의 페이지 전환이 이 타입을 재사용하므로 P3로 기록한다.

## 수동·통합 검증

#51은 scratch Git 저장소와 local bare 원격으로 아래를 확인했다. GitHub 원격에는 쓰지 않았다.

| 시나리오 | 관측 결과 |
|---|---|
| `HUSKY=0` 대조군 push | Git push 성공, 원격 LFS 객체 0개 |
| 실제 Husky 훅을 통한 push | 신규 원격 LFS 객체 1개, 내용 일치 |
| PATH에 git-lfs가 없음 | 훅 종료 코드 2, Git push 종료 코드 1, 원격 ref 불변 |
| mock LFS 실패 | 공백 포함 원격 인자와 stdin 2줄 보존, 종료 코드 37 보존 |
| 실제 신규 로컬 LFS 객체 누락 | 훅 종료 코드 2, Git push 종료 코드 1, 원격 ref 불변 |

#53의 브라우저 검증은 API 응답을 가로채는 기존 홈 화면 스모크다.
실제 로그인·SSE·댓글·장소 리뷰·지도 흐름을 확인한 것으로 해석하지 않는다.

## 실행하지 않은 검증과 남은 위험

- GitHub에 새 LFS 객체를 올리지는 않았다. 리뷰를 위해 원격 저장소에 시험 객체를 남기지 않았다.
- 실제 MySQL·Redis·백엔드와 연결한 테스트는 실행하지 않았다. 이번 검토는 로컬 코드·DTO와 프론트 검사에 한정했다.
- 네이버 지도 Client ID를 사용한 실제 SDK 로딩·길찾기는 실행하지 않았다. 전후 비교 빌드에도 자격 증명을 넣지 않았으므로 지도 로더의 일부 분기는 번들에서 제거된다. 해당 분기는 소스 diff로만 검토했다.
- 로컬 Gradle 테스트는 실행하지 않았다. 두 PR이 백엔드 실행 코드를 바꾸지 않았으며, 원격 백엔드 CI 성공만 확인했다.
- 전체 린트·취약점 검사는 재실행하지 않았다. 변경 파일 린트 결과를 전체 린트 성공으로 해석하지 않는다.
- R1의 실제 HTTP 응답·DB 왕복과 수정 후 검사는 실행하지 않았다. 인터페이스는 리뷰 대상 그대로 두었다.
- FE-15·FE-16·FE-17과 기존 보안 백로그는 이번 PR로 해결되지 않는다.
- #51의 `HUSKY=0`·`--no-verify` 우회 가능성은 기존에 명시한 제한이다.
